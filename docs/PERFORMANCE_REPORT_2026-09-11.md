# 模拟数据性能测试（2026-09-11）

## 结论

本轮模拟测试通过。3,000 个具有材料、进度、步骤、费用记录的订单下，20 个连续并发请求的整体 P95 为 383 ms，最大 482 ms，无 HTTP 错误或超时。当前无需因这组负载增加 Redis。首先达到上限的是数据库 CPU，继续增加并发不会等比例提高吞吐。

## 环境与数据

使用本机 Docker Desktop 的独立容器与网络；应用 1 CPU / 768 MiB，PostgreSQL 17 为 1 CPU / 640 MiB，连接池 4，Node 堆上限 384 MiB，数据库 shared_buffers 128 MiB、work_mem 2 MiB。应用与数据库合计有 2 CPU 配额，不能等同于总共 1 CPU 的服务器。数据库使用临时卷，应用使用 tmpfs 临时附件目录；没有向当前部署写入压测订单。

300 客户、10 项目、3,000 订单、3,000 申请人、30,000 材料、30,000 进度、15,000 步骤和3,000 费用计划。初始数据库含索引约 73 MB。订单状态均为 ACTIVE，使用单个 OWNER 会话。数据库连接使用测试库 owner，最小权限角色不属于本轮测量范围。

## 读取结果

顺序执行每档25秒，无用户思考时间的闭环并发。8个端点均匀轮换：订单首页、第80页、备注关键词搜索、常见中文搜索、拼音搜索、工作流详情、财务详情、仪表盘。测量包含响应体接收，不含浏览器渲染与公网延迟。数值为实际采样，未做多轮统计置信区间。

| 连续并发请求 | 请求数 | P50 | P95 | 最大 | 请求/秒 |
|---|---|---|---|---|---|
| 1 | 2545 | 4 ms | 23 ms | 32 ms | 101.8 |
| 5 | 2196 | 72 ms | 176 ms | 196 ms | 87.6 |
| 10 | 2011 | 103 ms | 206 ms | 297 ms | 80.1 |
| 20 | 2052 | 216 ms | 383 ms | 482 ms | 81.4 |

索引仍在构建时的5并发20秒测试：3,134请求，P95 86 ms，零错误。它与索引完全构建后的数据状态不同，不能直接作为性能提升对照。

随后5并发持续60秒：5,134请求，P95 178 ms，最大276 ms，零错误。全部已记录读取阶段共 **17072 请求、0错误**。这是短时持续测试，不是长时间稳定性或内存泄漏证明。

每5秒异步采样：应用约148–151 MiB、数据库约108–127 MiB；这不是瞬时峰值，也不包含 Docker VM、宿主系统和备份进程开销。无 OOM、无容器重启。5并发以上数据库接近1核配额，吞吐约80–88请求/秒。20并发时搜索端点 P95 最高398 ms。请求并发不等于在线用户数。

## 写入及回归

5并发创建100个带申请人、10项材料、步骤和费用计划的订单：全部成功、100个唯一单号，总耗时473 ms，P95 53 ms，最大67 ms。小样本、热缓存、临时测试存储下的结果不能作为生产持久化写入吞吐承诺。

随后在3,100订单环境运行集成测试：8项通过、0跳过、0失败。覆盖深层/拼音搜索、分页、单版本并发更新1成功4冲突、客户修改触发索引更新、20 MiB上传及超限拒绝、PDF范围下载和替换、项目模板按需加载。全部索引队列最终清空。

## 使用判断与未覆盖范围

目前这组数千订单、短时20并发结果支持继续使用现有数据库索引方案。不要根据空闲内存或本轮采样将容器上限直接降到采样值。

未覆盖：数万/十万订单、真实用户权限组合、每订单大量历史文件、多人同时大文件传输、小时级稳定性、冷缓存、备份并发干扰、真实低配CPU和机械磁盘、公网网络、故障恢复。常见中文2字和广泛匹配搜索仍需在更大数据规模下测试。当前搜索后台每轮最多20个任务，大批量导入会有索引等待，正常零星修改不等于大批量导入。
