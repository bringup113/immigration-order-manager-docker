# 当前性能基线

更新日期：2026-10-01。本文记录当前源码最近一次可复核的隔离测试结果。结果用于比较代码和配置变化，不能直接当作其他服务器的容量承诺。

## 测试环境

- 主机：Apple Silicon Mac，Docker Desktop 分配 10 个 CPU、约 7.47 GiB 内存。
- 应用：当前生产镜像，限制 1 CPU、768 MiB，数据库连接池 5。
- PostgreSQL 17：限制 1 CPU、640 MiB。
- 数据：3,000 订单、300 代理、10 项目、3,000 申请人、30,000 材料、30,000 进度、15,000 步骤和 3,000 费用计划。
- 请求范围：桌面／手机订单列表、三类搜索、订单流程／收支／申请人页签、桌面工作台、手机提醒翻页。
- MRZ：Docsaid `two_stage` CPU 模型，`linux/amd64` 镜像在 Apple Silicon 上模拟运行；使用一张本机测试护照图片重复识别。

数据库和应用位于专用临时网络及临时存储。本次未连接或修改 NAS，也未向公网发送测试图片。

持续测试共完成 20,662 个请求。结束时搜索任务为 0，3,000 条订单均有索引；应用与数据库空闲内存分别约 107 MiB 和 128 MiB。资源采样不是峰值监控，正式服务器仍应使用系统监控记录测试期间的 CPU、内存和磁盘 I/O。

常见词“材料”会命中较多内容，是本轮最慢的搜索：5 并发稳定态 P95 约 81 ms，20 并发 P95 约 103 ms。当前 PostgreSQL 索引足够这组模拟数据使用，没有增加 Redis 或独立搜索引擎的依据。

## MRZ CPU 与内存

| CPU 配额 | 完整次数 | 处理 P50 | 处理 P95 | 峰值 RSS | 结果 |
| --- | ---: | ---: | ---: | ---: | --- |
| 不限额 | 5 | 721 ms | 1,038 ms | 954 MiB | 5/5 成功并检出 |
| 0.5 CPU | 3 个已完成后停止 | 约 30.3 s | 约 32.9 s | 954 MiB 以内 | 过慢，不采用 |
| 1 CPU | 3 | 11.49 s | 11.68 s | 953 MiB | 3/3 成功并检出 |
| 2 CPU | 3 | 4.05 s | 4.59 s | 971 MiB | 3/3 成功并检出 |
| 4 CPU | 3 | 1.91 s | 2.11 s | 971 MiB | 3/3 成功并检出 |

这个模型会并行使用多个 CPU 核心，硬性限制为 1 CPU 在本机使单张识别延迟增加约 16 倍。当前单 worker、最多 3 个等待任务的队列已经限制并发争抢，因此继续使用“不设 CPU 配额、内存上限 1536 MiB”更合适。实测峰值接近 1 GiB，不能把内存上限降到 1 GiB；1536 MiB 留有必要余量。

MRZ 结果只来自一张样本，并且运行在 amd64 模拟环境。x86_64 服务器应按同一脚本重新测量；不同国家护照、图片尺寸、角度、光线和 PDF 仍需要独立准确率样本。

## 当前判断

- 10 人左右的日常使用量远低于本轮无思考时间的持续并发，当前应用查询、分页和 PostgreSQL 搜索结构有充足余量。
- 先保留 PostgreSQL 搜索，不引入 Redis；后续只有在真实数据和查询标识日志证明存在稳定瓶颈时再增加缓存。
- MRZ 保持独立服务、单 worker、有限队列、1536 MiB 内存和不限 CPU。服务器运行状态可展示资源信息，但不应让应用修改宿主机或容器资源配额。
- 每次改变查询结构、搜索索引或 MRZ 依赖后，按[隔离性能测试说明](../tests/performance/README.md)重跑并替换本文结果。
