# MIGRA 开发约束

## 可读性与文档维护

- 源码按正常缩进展开；一行只表达一个主要语句，复杂JSX按结构换行，不手工压缩源码。构建产物由工具压缩。
- UTF-8、LF、TS/JS两空格、Python四空格；编辑器遵循根目录.editorconfig。
- 页面负责展示与交互，路由负责鉴权、输入与响应，业务规则放在lib领域模块中；保留同一事务中的业务写入与审计边界。
- 同一接口的返回类型复用一个来源；可通过import type引用，避免前端加载服务端模块。新业务数据不要继续扩大Record通用类型。
- 修改大型页面时逐步抽取独立子表、表单和钩子；格式化和业务逻辑修改分开验证，避免一次重写整个订单模块。
- 不为“清理”删除数据库迁移、许可文件或未经核对的附件。停用依赖必须检查源码、Docker构建脚本、锁文件和测试。
- 文档按README中的分工维护：直接修改现状，删除已失效方案及重复流水账。历史性能报告只保留可复核证据和测试局限。
- 测试优先检查输入输出和权限行为；不得仅靠页面文案或代码字符串匹配证明业务正确。静态审计测试是补充，不代替集成测试。

## 功能、权限、日志必须同时交付

任何新增、修改或删除业务功能，都必须在同一个改动中完成以下检查：

1. 明确读取权限与写入权限，服务端接口必须校验，不能只隐藏前端按钮。
2. 前端按相同权限隐藏或禁用入口，避免给只读用户展示无效操作。
3. 成功与失败操作写入操作日志；新增、修改、删除、排序、作废、恢复、分配、导出、上传、下载和安全拦截都要有稳定的动作代码。
4. 项目包使用 `migra-project-package` / `1.0` 版本化 JSON；导入必须先校验完整结构和依赖，再在单一事务内写入。覆盖项目只替换项目模板，禁止修改订单快照。
5. 日志记录真实业务对象标识，并对密码、令牌、密钥、护照号等敏感字段脱敏。
6. 更新操作日志页面的中文动作名称；新增权限时同步更新权限依赖和权限测试。
7. 管理自定义角色用户时，不只比较内置角色名称；必须同时比较目标角色的权限集合和订单范围。操作者不得修改、停用、重置密码或撤销会话给权限或数据范围高于自己的账号。
8. 涉及多人并发的数据必须在数据库事务内校验版本，不能只在事务外先读后写。

代码评审或上线验收时，任一项缺失都视为该功能尚未完成。

## 申请人资料分阶段录入

- 新建订单及新增/修改申请人只要求系统显示名称；护照号、国籍、出生日期、有效期和护照首页允许后补。
- 草稿订单开始办理不检查申请人身份资料完整度或护照首页附件；只有显示名称也可开始办理并启动首个待办流程。材料完整度仍用于提醒，不作为启动门槛。
- 缺少护照号码使用数据库NULL，不能生成假护照号。填写后仍校验同订单护照号唯一性及字段格式。
- 护照首页材料位置自动建立，但上传不是新建订单的前置条件；MRZ人工确认仍需真实文件与完整校验资料。

## 数据类型与输入校验

- 只表示年月日的业务日期统一使用 PostgreSQL `date`；创建时间、更新时间、登录、会话和日志时间统一使用 `timestamptz`。
- PostgreSQL 驱动在应用边界把 `timestamptz` 规范为 ISO 8601 字符串，`date` 保持 `YYYY-MM-DD`，页面不得自行猜测时区。
- 服务端输入必须使用 `lib/validation.ts` 中的统一 Zod 校验；不能只依赖 HTML 输入类型或前端长度限制。
- 姓名、联系方式、护照号、标题、说明、备注和数组数量必须设上限。日期必须是实际存在的日历日期，枚举和币种必须使用白名单。
- 数据库约束是最后一道防线；接口校验不能替代外键、唯一约束、检查约束和原生字段类型。

## 订单流程规则

- 流程状态修改统一调用 `lib/order-workflow.ts`，路由和页面不得各自拼接状态转换 SQL。
- 每张订单最多一条 `IN_PROGRESS`。活跃订单没有当前步骤时，自动启动最前面的待办步骤。
- 完成或跳过当前步骤后自动启动下一条待办步骤；手动指定新的当前步骤时，原当前步骤退回待办。
- 必办步骤只有 `orders.override` 权限可以强制跳过，且必须填写原因。
- 暂停、取消、退款，以及从这些状态重新开启订单，必须填写原因。
- 流程序号在数据库中按订单唯一，排序必须在同一事务内锁定并交换。

## 订单负责人和数据范围

- 每张订单必须有且只有一名负责人。新订单默认由创建人负责；只有 `orders.assign` 权限可以在创建时指定他人或后续更换负责人。
- 角色订单范围只有 `ALL` 和 `OWN`。系统所有者始终按 `ALL` 处理；内置管理员和只读用户默认也是 `ALL`；自定义业务员角色通常使用 `OWN`。
- 所有订单衍生数据必须通过 `lib/order-access.ts` 的统一条件限制，不能只过滤订单列表。详情、直接 URL、首页统计、提醒、搜索、收支、申请人、材料、文件预览和下载都必须同步应用范围。
- `OWN` 用户访问他人订单及其文件时统一返回不存在，不能通过错误差异泄露对象是否存在。
- 全局搜索中的订单结果必须受范围限制；为 `OWN` 用户返回代理或项目搜索结果时，只能返回与其可访问订单相关的对象。
- 更换负责人必须在同一事务中记录修改前后值。即使操作人把订单分配给他人、操作后不再可见，成功日志仍要保存新的负责人。

## 订单待办规则

- 首页提醒链接携带目标tab：收支为finance，流程/跟进/待办为workflow，申请人材料为people，公共材料为common。全局搜索沿用命中来源的tab；订单详情通过页面searchParams接收白名单页签并响应后续链接变化。仅切换页签，不定位行、不高亮、不自动打开编辑弹窗；不新增业务写入或审计动作，继续执行现有订单范围和页签读取权限。

- 待办只属于具体订单，不建立独立顶级业务模块；页面入口放在订单“办理与跟进”内，首页只汇总今天、近期和逾期提醒。
- 待办包含标题、截止日期、优先级、状态、负责人及可选关联对象。关联对象只能是同一订单内的流程、申请人、材料或收付款计划。
- 同一订单允许多个未完成待办。完成时必须写入 `completed_at`，重新打开时必须清空；数据库约束负责兜底。
- 待办使用 `tasks.read` / `tasks.write` 权限，并始终继承所属订单的 `ALL` / `OWN` 数据范围。
- 新增、修改、完成、重新打开和删除分别使用稳定的 `TASK_CREATE`、`TASK_UPDATE`、`TASK_COMPLETE`、`TASK_REOPEN`、`TASK_DELETE` 日志代码。

## 审计事务标准

- 关键业务写入与成功日志必须使用同一个 `AppDatabase.transaction` 和同一个事务对象；日志写入失败时业务写入必须回滚。
- 修改和删除日志至少保存关键字段的 `before` 与 `after`；提交内容只能作为补充，且统一经过敏感字段脱敏。
- 业务失败日志在主事务回滚后以 best-effort 方式另行记录；失败日志自身写入失败时必须输出结构化的 `audit_write_failed` 错误，便于容器日志监测。
- 文件预览、下载等只读访问不应因日志故障阻断用户读取，但必须调用 `writeAuditBestEffort` 并保留失败监测。
- 文件上传、删除等同时涉及磁盘和数据库时，先使用临时或隔离路径，再把数据库写入和审计放入同一事务；事务失败必须恢复或删除相应磁盘文件。

## 备份边界

- 自动和手动备份只包含 PostgreSQL 数据库。
- `data/files/` 上传文件不进入服务器备份，文件原件由使用者在电脑端留档。
- `APP_AUTH_SECRET` 或 `data/.auth-secret` 不是上传文件；启用双重验证后必须在密码管理器中单独安全留存，否则迁移服务器后无法解密 TOTP 密钥。

## PostgreSQL 备份与恢复标准

- 新备份只使用 `pg_dump -Fc` custom 格式，不再生成或兼容旧 `.sql.gz` 脚本。
- `pg_dump` 必须直接写入同目录临时文件，禁止使用可能吞掉前序错误码的压缩管道；自动与手动备份使用同一把跨进程锁。
- 正式恢复与备份使用同一把锁；只有实际取得锁的进程可以在退出时释放它，等待者不得删除持有者的锁。
- 临时文件只有在最小大小和 `pg_restore --list` 表数据目录检查均通过后才能原子改名为正式 `.dump`；失败必须删除临时文件并输出稳定的 `backup_*_failed` 日志事件。
- 每次发布前使用 `restore-drill-postgres.sh` 将最新备份恢复到隔离数据库，运行全部迁移、数据统计和文件一致性检查，完成后自动删除隔离数据库。
- 正式恢复使用 `pg_restore --single-transaction --exit-on-error`，随后必须重新运行 `postgres_migrate`，恢复 migrator/runtime/backup 的对象归属与最小权限。数据库恢复或迁移失败时应用必须保持停止；附件一致性异常可以在生成报告后重启应用并返回非零状态。

## 数据库与容器权限标准

- PostgreSQL owner 只用于初始化和维护；migrator 只在一次性迁移容器中使用；Web 长期使用 runtime；备份容器只使用 backup。
- runtime 与 backup 均必须是 `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`。backup 只允许读取；runtime 不允许修改或删除操作日志和结案历史。
- Web 启动时设置 `SKIP_DATABASE_MIGRATIONS=1`，不得把 DDL 权限重新授予运行账号。
- 应用镜像必须以构建时写死的非 root UID/GID 运行；只允许写入 `/app/data` 和临时目录，应用代码目录保持只读。
- `.env` 必须是 `0600`；应用和备份容器使用 `APP_UID:APP_GID` 访问宿主机绑定目录，避免 Linux 上目录归属不同导致写入失败；所有容器使用 `json-file` 大小与文件数轮转，禁止无限增长。

## 会话与密码标准

- Docker 会话同时执行空闲超时和绝对超时，默认分别为 60 分钟与 12 小时；参数只能在代码允许范围内调整。
- 用户可查看自己的有效会话、退出单个其他设备或退出其他所有设备；这些动作必须受同源校验、限定当前用户范围并写成功/失败日志。
- 修改密码和管理员重置密码继续撤销该用户所有有效会话。过期会话及时删除，长期撤销会话按保留期清理。
- 新密码使用 PBKDF2-HMAC-SHA256 600,000 次；登录成功时自动升级低迭代旧哈希。密码长度统一限制为 10–128 个 Unicode 字符。
- 已启用 MFA 的账号更换验证器时，必须先验证当前密码和原 TOTP 或恢复码；验证凭据应短期有效并绑定用户及原密钥。恢复码的检查和删除必须在锁定用户记录的同一事务内完成，确保并发请求只能成功一次。
- `PUBLIC_DEPLOYMENT=1` 时，系统所有者未启用 MFA 只能访问个人安全设置，不能继续业务操作，也不能关闭 MFA；管理员和其他账号可按需启用。

## 内外网来源校验标准

- `APP_ORIGIN` 只保存一个正式公网 HTTPS 来源，按 URL origin 精确比较；非标准端口必须写入，路径不得写入。
- NAS 内网直连不加入 `APP_ORIGIN`。请求携带的浏览器 Origin 与 `Host` 或可信代理传入的 `X-Forwarded-Host` 相同时，视为同源并允许登录和业务写入。
- `Sec-Fetch-Site: cross-site` 必须优先拒绝；公网来源、内网同源和无 Origin 的非浏览器请求都不能绕过已有会话与权限校验。
- Lucky 等反向代理必须传递原始 Host，并将 `X-Forwarded-Proto` 设置为外部实际协议；否则 HTTPS 登录 Cookie 和重定向可能不正确。
- 内网地址与公网域名的 Cookie 隔离，用户切换入口时需要分别登录，这是浏览器同源模型的正常结果。

## CI 与发布门禁

- CI 固定顺序为：安装锁定依赖 → lint → 权限/审计及领域单测 → 备份失败测试 → 全新挂载目录准备测试 → Docker 构建启动 → 创建确定性测试夹具 → PostgreSQL 与业务全链路集成测试 → MRZ 流式传输边界测试 → 浏览器搜索回归 → 当前订单流程浏览器回归 → 会话安全测试 → 删除测试数据 → 容器和数据库权限验证 → 隔离恢复演练。
- 镜像发布任务必须 `needs: verify`；任一检查失败时不得登录镜像仓库或发布标签。
- `test:integration` 必须明确提供隔离应用地址、隔离数据库和临时账号；启动脚本发现缺少环境变量时直接失败。订单生命周期、本人订单范围、材料文件、收付款、结案、日期联动、分阶段申请人、排序、提醒和审计完整性不得以跳过代表通过。
- MRZ 传输测试必须设置 `MIGRA_MRZ_TRANSFER_TEST=1`，并把测试应用的 sidecar 地址指向同一隔离网络中的受控测试容器；不得对生产识别服务执行超限和并发占位测试。
- 数据库专项测试优先使用连接级临时表；需要写业务表时必须使用可重复清理的随机数据或固定夹具，并在 `finally` 或 CI 的 `always()` 阶段清理。
- CI 创建的临时账号密码只写入 Runner 临时文件；密码先通过 GitHub Actions `add-mask` 注册，再注入后续测试步骤。固定测试夹具与账号必须在备份恢复演练前删除，失败清理步骤再次兜底，避免测试资料进入备份。

## 确认弹窗标准

- 删除、停用、作废、强制跳过以及需要填写原因的敏感状态变更，统一使用 `components/confirm-dialog.tsx`，不得使用浏览器原生 `window.confirm` 或 `window.prompt`。
- 弹窗必须明确说明操作对象、影响范围和能否恢复；删除类确认按钮使用红色，非破坏性敏感操作使用系统绿色。
- 需要原因的操作在同一弹窗内显示文本框，原因未填写时不能确认；提交期间锁定关闭和重复提交。
- 普通保存、排序和可轻易撤销的交互不额外弹窗，避免无意义确认干扰正常操作。
- 新页面增加危险操作时必须复用统一组件，并同步检查服务端权限、操作日志与自动化测试。

## 材料文件版本与一致性

- 文件记录状态只使用 `ACTIVE`、`SUPERSEDED`、`VOIDED`；当前页面默认只显示有效文件，历史文件不得混入当前材料结果。
- 同一材料允许多个有效文件。“替换”只针对用户选定的一个有效文件，新文件通过 `superseded_by_id` 与原文件建立版本关系，必须填写原因。
- 作废不物理删除文件；恢复需要 `materials.restore`。上传、替换、作废、恢复分别使用稳定日志代码，并保存哈希、状态和前后值。
- 新上传文件必须计算 SHA-256。`scripts/check-file-integrity.mjs` 只能读取，报告缺失文件、孤儿文件、大小不符和哈希不符，绝不能自动删除或修复。
- 孤儿文件必须逐项核对并取得用户确认后才能删除；一致性测试创建的临时文件必须在测试结束时清理。

## 订单收支历史与利润口径

- 选择关联计划时，说明为空或仍为本次自动填入的名称，才填入所选阶段名称。手动修改或已保存的说明保留；取消关联或切换收付方向保留说明并结束自动联动，再选计划时按普通文本处理。每次打开新建/编辑窗口重新初始化自动填充状态，仅作为前端草稿信息，不写入数据库。

- 收付款记录只使用 `ACTIVE` 和 `VOIDED`；不再提供物理删除。作废必须填写原因，恢复需要 `finance.restore`。
- 作废记录不得参与计划完成金额、实际已收、实际已付、首页汇总、趋势或利润，但仍保留在详情历史和搜索索引中，并明确标记“已作废”。
- “预计利润”固定为计划应收减计划应付；“订单利润”固定为实际已收减实际已付。订单未结案时，后者必须标记为“当前订单利润”。
- 首页计划未结清金额以计划原币的剩余金额判断；换算本位币时按该计划保存的本位币与原币比例折算。计划原币已经结清时，即使实际收付使用了不同汇率，也不得产生虚假的未结清提醒。
- 修改收付款记录时，成功日志必须包含日期、方向、说明、币种、原币金额、汇率、本位币金额、计划关联及备注的前后值。

## 订单结案规则

- 订单不能通过普通状态下拉框直接改为完成，必须使用正式结案操作；已结案订单只能通过“重新开启”恢复办理。
- 结案前汇总未完成必办流程、缺少必需材料、未完成待办、未完成跟进和计划/实际收付。材料、待办、跟进及未结清金额只警告，不阻止结案。
- 未完成必办流程时，只有 `orders.override` 可以强制结案，并且必须填写原因。重新开启同样需要该权限和原因。
